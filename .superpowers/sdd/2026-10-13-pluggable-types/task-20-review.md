## Blocking findings

1. **Sensitive connection configuration loses protection when its provider is absent.** `internal/controlplane/network_connections.go:121-144` starts with an empty descriptor and still returns sanitized raw configuration when no registered descriptor matches a persisted type. `internal/connections/secrets.go:120-145,176-203` can then redact sealed-secret values and heuristic credential keys, but cannot recognize a formerly `Sensitive` field with an ordinary name. Trigger: register an extension with sensitive text `client_id` or sensitive keyvalue `env`, save it, restart with the provider unregistered, then read Connections as an organization member. Values unrelated to sealed secrets pass through unchanged. This violates descriptor-owned sensitivity across retained unavailable-provider records. Smallest fix: fail closed for unavailable descriptor config and runtime details (retain safe identity/unavailable status), with an API regression containing a nonheuristic sensitive field and a missing registry entry. A persisted unavailable service driver does not have this particular leak: FromRecordWithRegistry returns an empty Definition on error.

2. **Topology returns raw service driver diagnostics.** `internal/controlplane/topology.go:320` assigns `st.LastError` directly to a member-readable node detail. The manager retains raw driver errors (`internal/services/manager.go:619` and other error paths); service DTOs deliberately mask these at `network_services.go:79-81`, but the map bypasses that protection. Trigger: a custom descriptor driver reports an error containing a sensitive config value, or a Command failure includes an executable name also present as a sensitive environment value. GET services masks the diagnostic; GET topology exposes it. Smallest fix: apply the same generic safe diagnostic to service topology details and verify a credential-bearing status does not appear in topology JSON. Keep safe state and service identity.

3. **Cloudflare token guidance omits a permission used by managed publication.** `web/src/components/cloudflare/ManagementSection.tsx:3-7` presents the required permission list without `Zone · Zone · Read`. Managed DNS reconciliation always resolves the hostname zone with GET `/zones` (`publisher.go:575-581`, `client.go:291-301`); `docs/cloudflare.md:57` correctly lists this permission. An operator following the displayed list can create a token unable to resolve zones and publish DNS. Smallest fix: add the missing required permission to the UI guidance, consistent with the docs. This is a concrete setup defect, not an additional account authorization request.
